# L0→L3 Agent 协同设计

> 法人小微企业授信尽调 · SDAFI v2.0 架构落地
> 配套文档:Agent 对应矩阵最终版 · 玉林普惠金融信用评级与风控方案 · SDAFI 白皮书 v2.0
> 版本:2026-05

---

## 摘要

L0→L3 是法人尽调 16 个 Agent 的**横向调度结构**,与 SDAFI 五阶段(纵向时间线)是两个互补的视角:

- **SDAFI 五阶段**管单 Agent 内部的运行纪律(每个 Agent 都跑完整 S→D→A→F→I)
- **L0→L3 分层**管 Agent 之间的调度关系(谁指挥谁、谁等谁、信号怎么传)

少了 L0→L3 视角,工程团队不知道 16 个 Agent 之间怎么协作——谁串行、谁并行、关键路径多长、Critic 在哪一层拦截。这份文档补齐这一层。

---

## 一、L0→L3 各层定义

| 层 | 名称 | 包含 Agent | Agent 数 | SDAFI 阶段 | 关键纪律 |
|---|---|---|---|---|---|
| **L0** | 编排层 | SE-01 | 1 | Sense | 一票否决前置 + 快照冻结 + 任务下发,不做业务判断 |
| **L1** | 原子工具层 | 4 个 MCP 工具组 | 0 | Sense 子组件 | 哑工具,只调 API 不判断,所有结果写数据池 |
| **L2** | 章节分析层 | LE-A01 ~ LE-A06 | 6 | Decide | 6 个 Agent 完全并行,产物互不依赖 |
| **L2.5** | 横向分析层 | LE-A07 ~ LE-A09 | 3 | Decide | 等 L2 全部完成后并行启动,只读 cycle_log + 数据池 |
| **L3** | 决策与质检层 | LE-A10 / LE-A11 / LE-A12 | 3 | Decide | LE-A10 + LE-A11 并行 → LE-A12 Critic 串行核查 |
| **Act** | 执行层 | AC-01 | 1 | Act | 唯一写业务库 → 推审批官 |
| **闭环** | 反馈与改进 | FB-01 / IM-01 | 2 | Feedback / Improve | 长期运行,贷后回写 + 季度改进 |

**说明**:SDAFI 的 16 个 Agent 完整对应到 L0→L3 + Act + 闭环。L0/L1 在传统 LangChain 里通常并称"工具层",这里拆开是因为 SE-01 是有判断的(否决/授权),L1 是纯哑工具,职责本质不同。

## 三、协同的三种调度模式

L0→L3 的协同**不是单一 DAG**,而是三种模式交织。

### 模式 A · 扇出并行(L2 内部)

SE-01 把任务下发后,L2 的 6 个 Agent **同时启动、互不等待**。LE-A01 不知道 LE-A04 在干什么,也不需要知道——它们都从同一份数据池快照读字段,各自写自己的 cycle_log。这是 SDAFI 纪律三的直接落地:Agent 间零直接调用。

**工程实现**:
- 消息队列(MQ):SE-01 发布 `snapshot_ready` 事件,6 个 Agent 各自订阅
- 数据池广播:所有 LE-A0x 共享同一个 snapshot_id,只读
- 失败隔离:某个 Agent 跑错不影响其他 Agent,各自重试

### 模式 B · 屏障同步(L2 → L2.5)

L2.5 的 3 个 Agent 必须等 L2 **全部 6 个 Agent 完成**才能启动。LE-A07 交叉验证要读 LE-A04 的发票汇总和数据池中的用电字段,如果 LE-A04 还在跑,LE-A07 就拿到半成品。

**工程实现**:
- cycle_log 加 `barrier_event` 字段
- L2.5 的 Agent 监听"6 个 LE-A0x 都状态 = finished"才触发
- 这是关键路径上**唯一不能并行的串等点**

### 模式 C · 串行核查(L3 内部)

LE-A10 + LE-A11 可以并行(评级和贷后监控互不依赖),但 LE-A12 Critic 必须**等他俩都完成才启动**。Critic 的工作是反向核查整份报告的一致性。

**特殊性**:Critic 多了一个反馈回路——不通过则**退回对应 Agent 重写**,最多 2 轮,超过 2 轮转人工。这个回路在调度图里是一条向上的虚线,工程上需要支持有界循环。

## 四、Critic 回路的具体规则

LE-A12 是 L3 最重要的 Agent,其拦截规则需要清楚定义,否则会变成"什么都退回",拖死系统。

### 三类拦截规则

**1. 数据对账型不一致 → 退回对应 LE-A0x**

例:LE-A06 给的财务健康分是 80,但 LE-A04 报告说"资产负债率 75%"——按评分规则应是 30 分,前后矛盾。退回 LE-A06 重算。

判断逻辑:
```
if abs(LE-A06.财务健康度得分 - rule_based_score(LE-A04.关键比率)) > 15:
    return REJECT(target=LE-A06, reason="数据对账偏差>15分")
```

**2. 跨章节逻辑型不一致 → 退回写报告的 Agent**

例:LE-A02 实控人画像说"无负面",LE-A10 授信建议却写"加强法人风险条款"——前后矛盾。退回 LE-A10 重写授信建议章节。

判断逻辑:
```
if LE-A02.法人负面 == "无" and "法人风险" in LE-A10.授信建议特殊条款:
    return REJECT(target=LE-A10, reason="授信建议与实控人画像矛盾")
```

**3. 一票否决项遗漏 → 紧急退回 SE-01,并触发 IM-01 复盘**

例:Critic 发现数据池里有"严重违法"标签,但 SE-01 没拦下。这是最严重情况,**必须打到 IM-01**(IM-01 改 SE-01 的否决规则)。

判断逻辑:
```
if any(veto_flag in snapshot for veto_flag in VETO_LIST):
    if not SE-01.veto_triggered:
        emergency_alert()
        FB-01.write(severity="CRITICAL", agent=SE-01)
        IM-01.queue_review(quarterly=False, urgent=True)
```

**注**:第三种情况触发 SDAFI 闭环里的 F→I 路径——Critic 反向驱动模型治理。这是 Critic 不仅做"质检"还做"系统进化"的体现。

### 重试预算

| 第 N 轮 | 动作 | 预算 |
|---|---|---|
| 第 1 轮 | LE-A12 不通过 → 退回 LE-A0x → 重跑 → 再 Critic | +50-60 秒 |
| 第 2 轮 | LE-A12 仍不通过 → 再退回一次 | +50-60 秒 |
| 第 3 轮 | **不再重试,转人工** | 切换到客户经理 |

## 五、关键路径与时长估算

将上述协同规则落到时间轴,一笔授信申请的端到端时长如下。

### 时序示意

```
0       15      30      45      60      75      90      105   秒
│───────│───────│───────│───────│───────│───────│───────│───────
                                                                
■■                                                              SE-01 否决前置 (5-8s, 7 接口并发)
   ■■                                                           授权门控 (3-5s)
      ■■■■                                                      SE-01 数据池抓取 (15-20s, 90+ API)
                                                                
              ▼ snapshot_ready
                                                                
          ■■■■■                                                 LE-A01 企业画像 (12-18s)
          ■■■■■                                                 LE-A02 实控人 (12-18s)
          ■■■■■■■■                                              LE-A03 行业经营 (含 RAG, 25-35s) ← 瓶颈
          ■■■■■■■                                               LE-A04 财务诊断 (20-30s)
          ■■■■■                                                 LE-A05 履约征信 (12-18s)
          ■■■                                                   LE-A06 五维评分 (8-12s)
                                                                
                              ▼ barrier(等最慢的 LE-A03)
                                                                
                                  ■■                            LE-A07 交叉验证 (5-8s)
                                  ■■■                           LE-A08 风险地图 (8-12s)
                                  ■■                            LE-A09 用途还款 (5-8s)
                                                                
                                       ▼
                                                                
                                       ■■                       LE-A10 授信结论 (5-8s)  ┐ 并行
                                       ■■                       LE-A11 贷后方案 (5-8s)  ┘
                                          ■■                    LE-A12 Critic (5-8s)
                                                                
                                             ■■■               AC-01 渲染 + 写库 (8-12s)
                                                                
                                                ▼ 三方签字
```

### 阶段耗时分解

| 阶段 | 耗时 | 是否在关键路径 |
|---|---|---|
| 客户经理录入 | 异步 | 否(在 Agent 启动前完成) |
| SE-01 一票否决前置(7 个无授权接口并发) | 5-8 秒 | **是** |
| 授权门控(H5 + 电签) | 3-5 秒 | **是**(被否决路径直接终止) |
| SE-01 数据池抓取(90+ API 并发 + 字段哈希) | 15-20 秒 | **是** |
| L2 并行(关键路径 = 最慢的 LE-A03) | 30-40 秒 | **是**(被 LE-A03 RAG 拉长) |
| L2.5 并行(关键路径 = 最慢的 LE-A08) | 12-15 秒 | **是** |
| L3 串行(LE-A10/A11 并行 → LE-A12 Critic) | 8-12 秒 | **是** |
| AC-01 渲染 docx + 写库 | 8-10 秒 | **是** |
| **合计(无 Critic 退回)** | **约 90-110 秒** | — |
| Critic 1 轮退回(L2 重跑某个 + 再 Critic) | +50-60 秒 | 偶发 |
| Critic 2 轮退回(超 2 轮转人工) | +120 秒 | 极少 |

### 几个工程结论

**1. LE-A03 是关键路径瓶颈**
RAG 检索行业研报需要向量数据库往返 + 大模型综合,会比其他 5 个 Agent 慢 1.5-2 倍。
**优化方向**:预热行业 RAG 缓存(同行业的研报检索结果缓存 24 小时),可以把 L2 段从 40 秒压到 20 秒。

**2. L1 工具组的并发度上限决定 SE-01 抓数耗时**
90+ API 并发抓不能真的并发 90 路,要看正菱接口侧的 QPS 限制。
**建议**:SE-01 分 5 批 × 18 路并发,避免触发供应商限流。

**3. Critic 退回是兜底,不是常态**
上线初期可能 20% 报告会被 Critic 退回(模型还没磨合好),稳定运行后应降到 5% 以下。如果稳定期超过 10%,说明 LE-Axx 的 Prompt 或评分规则需要 IM-01 改进。

**4. "决策可重现 30 秒可查"指的是事后查询**
白皮书 §10.1 的 30 秒承诺指的是查询审计表,不是端到端尽调耗时。这两件事不是一回事:
- 尽调要 105 秒
- 事后回查"为什么评成 B 级"只要 30 秒(查 5 张审计表)

## 六、L0→L3 协同的四条工程纪律

落到工程实施,L0→L3 协同必须守的四条纪律。

### 纪律一 · L0 不做业务判断,只做调度

SE-01 看到客户 A 的纳税信用是 D 级,**不能擅自决定否决**——D 级是 LE-A06 维度评分要做的判断,不是 SE-01 的范围。

SE-01 只判断硬性否决项,合计 7 项:

1. 失信被执行
2. 限制高消费
3. 疑似空壳(空壳指数超阈值)
4. 重大税收违法
5. 破产重整
6. 法人涉赌涉诈(银行卡风险标签)
7. 企业严重违法

其他都不归 SE-01 管。

### 纪律二 · L1 不做缓存判断

工具组拿到 API 返回后**不擅自做 NULL 判定**或字段重命名。

例:"近三月话费"接口返回空,L1 工具不能自动填 0——可能客户真没话费,也可能 API 故障,**两种情况下游处理完全不同**:
- 真没话费 → LE-A02 标记为"经营存续真实性疑点"
- API 故障 → SE-01 重试 / 报警 / 转人工补录

L1 老老实实把"空"写到数据池,让 LE-Axx 自己判断,**不替下游做决定**。

### 纪律三 · L2 内部禁止互相调用

LE-A04 财务 Agent 想知道企业行业类别(LE-A01 已经有),**不能直接 RPC 调 LE-A01**,只能从数据池读 `enterprise_meta.industry_code`。

这是白皮书纪律三"Agent 间零直接调用"在 L0→L3 调度结构上的具体体现。

**反模式**(不允许):
```python
# 错误示范
def le_a04_run():
    industry = le_a01.get_industry_code()  # 直接 RPC,违反纪律三
```

**正确做法**:
```python
def le_a04_run():
    snapshot = data_pool.read(snapshot_id)  # 从快照读
    industry = snapshot["enterprise_meta"]["industry_code"]
```

### 纪律四 · L3 Critic 不能被绕过

任何情况下 AC-01 都必须等 LE-A12 Critic 通过才能渲染——**不允许"快速通道"或"高分客户跳过 Critic"**。

Critic 是 SDAFI 体系的事实把关人,绕过就等于关闭审计。这一点在合规上是红线。

**实施层面**:AC-01 的入口检查代码必须包含
```python
def ac_01_render(cycle_id):
    critic_status = cycle_log.get(cycle_id, agent="LE-A12").status
    assert critic_status == "PASSED", "Critic 未通过,禁止渲染"
    # ... 后续渲染逻辑
```

## 七、与 SDAFI 五阶段的对照

L0→L3 与 SDAFI 五阶段是两个互补视角,放在一起才完整。

| 视角 | 关注点 | 颗粒度 | 主要回答的问题 |
|---|---|---|---|
| **SDAFI 五阶段** | 单 Agent 内部纵向时间线 | 一个 Agent | 这个 Agent 自己怎么跑?写哪张审计表? |
| **L0→L3 分层** | Agent 之间横向调度 | 16 个 Agent 之间 | 谁等谁?哪里并行?Critic 怎么拦? |

### 同一个 Agent 在两个视角中的表述

以 LE-A04 财务诊断为例:

**SDAFI 视角**:
- S(Sense):读数据池快照中的财务字段(三表 / 发票 / 纳税)
- D(Decide):比率分析、异动识别、生成第五章内容
- A(Act):产物入 cycle_log.output_ref
- F(Feedback):跟踪自身预警准确率
- I(Improve):基于反馈调整异动阈值

**L0→L3 视角**:
- 所属层:L2 章节分析层
- 上游依赖:SE-01 的 snapshot_ready 事件
- 并行同伴:LE-A01/A02/A03/A05/A06(扇出并行)
- 下游消费者:LE-A07 交叉验证(屏障同步后启动)
- 异常情况:被 LE-A12 Critic 退回时,根据反馈重新走一遍 SDAFI

两个视角缺一不可。

## 九、人在环 3 个节点

L0→L3 协同中保留 3 个人在环节点,任何自动化都不绕过。

## 十、小结

### 核心要点

1. **L0→L3 + Act + 闭环 = 16 个 Agent 完整协同结构**,与 SDAFI 五阶段是两个互补视角
2. **三种调度模式**:扇出并行(L2)、屏障同步(L2 → L2.5)、串行核查(L3 Critic 回路)
3. **关键路径约 90-110 秒**,LE-A03 RAG 是瓶颈,可通过缓存优化
4. **Critic 三类拦截规则**:数据对账 / 跨章节逻辑 / 一票否决遗漏,后者反向驱动 IM-01
5. **四条工程纪律**:L0 不做业务判断 / L1 不做缓存判断 / L2 内部零直接调用 / L3 Critic 不能被绕过
6. **3 个人在环节点**:申请录入 / 报告签字 / 模型改动审批
