## 1. 为什么需要 SDAFI

### 1.1 一个真实的监管现场提问

> "你们的 AI 系统是怎么判断这个客户授信通过的？把数据来源、决策步骤、模型版本完整调出来。"

这是 2025 年某省级银保监对一家试点 AI 智能体的银行的真实提问。该银行使用的是**通用 Agent 框架**（LangChain），现场无法在 30 分钟内调出完整证据链——Agent 之间通过自然语言协商，事后无法结构化回溯。

**结果**：该银行被要求**整改 3 个月**，AI 智能体业务暂停。

这暴露了一个普遍问题：**通用 AI Agent 框架在金融场景的合规缺口**。

### 1.2 通用 Agent 框架的三个合规缺口

#### 缺口一：决策输入瞬态

LangChain / CrewAI 等框架默认在内存中持有数据，进程结束即消失。监管问"基于什么数据决策"时，只能拿到大模型 prompt 日志（如果有的话），但 prompt 中的数据**没有时点**——你无法证明"这个数字是 2025-04-29 14:33:22 时点的纳税申报数据，而不是当天 16:00 的"。

#### 缺口二：协作链路无结构化记录

CrewAI 中两个 Agent 互相"协商"是通过自然语言对话。监管问"A Agent 是怎么说服 B Agent 的"——你只有对话日志，没有结构化的因果链。**对话日志不是审计证据**。

#### 缺口三：自修正历史空缺

通用框架不记录"为什么这个 Prompt 改了 / 为什么这个阈值调整了 / 上次模型升级前后效果差异"。监管问"你的模型在过去 6 个月做了哪些改进"——你拿不出系统性记录。

### 1.3 SDAFI 的论点

SDAFI（**S**ense-**D**ecide-**A**ct-**F**eedback-**I**mprove）不是通用 Agent 框架，而是**面向监管级回溯的业务 Agent 运行时**。

**核心论点**：
1. **审计能力必须是架构副产物，而不是事后补丁**
2. **每一次决策天然产出完整、结构化、可回放的证据链**
3. **跨实例、跨时间、跨版本一致**

通过五阶段闭环 + 五张审计表 + 四条架构纪律，SDAFI 在工程上保证：监管问任何关于"Agent 做了什么"的问题，都能用 SQL 在 30 秒内拿到答案。

## 2. SDAFI 五阶段闭环

### 2.1 五阶段定义

| 阶段 | 中文 | 业务问题 | 在金融场景示例 |
|---|---|---|---|
| **S - Sense** | 感知 | 看什么数据？看多远？ | 从 90+ API 实时感知企业经营全貌（贷前看历史 36 月，贷后实时事件驱动） |
| **D - Decide** | 决策 | 用什么模型？规则还是 AI？ | 五维评分（规则）+ 五对交叉验证（规则）+ 大模型推理（AI）三者结合 |
| **A - Act** | 执行 | 改什么？通知谁？ | 生成尽调报告 → 推送审批官 / 触发预警工单 / 调整监控配置 |
| **F - Feedback** | 反馈 | 预期 vs 实际？偏差多少？ | 跟踪每笔授信后续表现：正常还款 / 逾期 / 不良 |
| **I - Improve** | 改进 | 调什么参数？要不要重训？ | 子指标权重调优 / 阈值微调 / Prompt 优化 / 季度模型重训 |

### 2.2 闭环的本质

```
Sense → Decide → Act → Feedback → Improve
  ↑                                  │
  └──────────────────────────────────┘
            （持续自我进化）
```

传统"开环"系统（评分卡 / 规则引擎）：上线那天就停止学习。

SDAFI"闭环"系统：每一次决策的对错都被记录，反向驱动改进。

> "银行业最大的风控挑战不是'当下能不能识别风险'，而是'明年的风险特征是否还能识别'。欺诈手法在演变，经营模式在变化——任何静态评分卡式的系统，上线那天就开始过时。"
>
> SDAFI 闭环让 Agent 像有经验的客户经理一样，**能从每一次决策的对错中学习**。

### 2.3 与传统 BI/ML 闭环的差异

| 维度 | 传统 ML 闭环（A/B 测试） | SDAFI 闭环 |
|---|---|---|
| 反馈周期 | 数月（等模型迭代） | 实时 + 季度 |
| 反馈粒度 | 模型整体 | 单 Agent / 单 Prompt / 单阈值 |
| 可解释性 | 弱（黑盒模型）| 强（每步推理留痕） |
| 监管友好度 | 弱 | **架构级强约束** |
| 自动化程度 | 半自动（需数据科学家） | 业务侧规则即自动 |

### 2.4 五阶段的"一进一出"原则

**关键纪律**：每个阶段必须有清晰的**输入契约 + 输出契约**。

| 阶段 | 输入 | 输出 |
|---|---|---|
| Sense | API 调用规格 + 时间范围 | 数据池快照（不可变） |
| Decide | 数据池快照 + Agent 配置 + Prompt | 决策结果 + 推理轨迹 |
| Act | 决策结果 | 业务库变更 + 通知 |
| Feedback | 业务库实际表现 | 偏差数据 |
| Improve | 偏差数据 + 人类决策 | 配置变更（Prompt / 阈值 / 模型） |

每一进一出都对应一张审计表（详见 §3）。

## 3. 五张审计表 · Audit-by-Design 的工程化体现

> 这是 SDAFI 的核心论点：**SDAFI 的 S→D→A→F→I 五阶段闭环不只是方法论，在工程上对应五张审计表**。每一次 Agent 决策循环，都会在这五张表中原生留下完整证据，无需任何额外的审计代码。

### 3.1 五张审计表的业务层规格

> 实施方可选择具体存储实现（关系型 / 文档型 / 时序数据库等），但必须保证五类证据可 SQL 检索、可时序回放。

#### 表 1 · device_pool / revenue_pool（数据池快照）

回答**"基于什么数据决策？"**

| 字段（业务最低集合）| 含义 |
|---|---|
| `snapshot_id` | 全局唯一快照 ID |
| `customer_id` | 客户号 |
| `api_source` | API 来源（例：`正菱.企业核心财务指标`）|
| `api_field` | 字段名（例：`accounts_receivable_days`）|
| `value` | 字段原始值 |
| `observed_at` | 观测时间戳（精确到秒）|
| `data_pool_type` | `device_pool` / `revenue_pool` / 其他 |
| `hash` | 字段值哈希（用于完整性校验）|

**关键约束**：
- 每次报告生成时**冻结一次快照**（snapshot_id 全局唯一）
- 同一报告所有 Agent 看到的数据为同一快照
- 快照不可变（一旦写入，禁止修改）
- 保留至贷款清偿 + 5 年

#### 表 2 · cycle_log（决策循环日志）

回答**"怎么决策的？"**

| 字段 | 含义 |
|---|---|
| `cycle_id` | 单次 Agent 调用的全局唯一 ID |
| `agent_id` | 例：`LE-A05` |
| `agent_version` | 版本号 |
| `model_version` | 大模型版本（如使用） |
| `prompt_template_id` | Prompt 模板版本 |
| `input_ref` | 输入引用（指向数据池快照 + 上游输出）|
| `output_ref` | 输出引用 |
| `rule_hits` | 命中的业务规则（例：`["阈值超出","行业偏离"]`）|
| `started_at` / `finished_at` | 时间戳 |
| `status` | success / partial_success / failed / skipped |

**关键约束**：
- 每次 Agent 调用必须产出一条 cycle_log
- 输入输出可通过 `input_ref` / `output_ref` 完全还原
- prompt 全文可通过 `prompt_template_id` 重建（含变量替换）

#### 表 3 · agent_signal_log（Agent 协作信号）

回答**"谁触发了谁？"**

| 字段 | 含义 |
|---|---|
| `signal_id` | 信号 ID |
| `from_agent` | 上游 Agent ID |
| `to_agent` | 下游 Agent ID |
| `signal_type` | `data_dependency` / `trigger` / `notification` |
| `payload_ref` | 载荷引用 |
| `occurred_at` | 时间戳 |

**关键约束**：
- 任意两个 Agent 之间的输入输出**必须**以信号形式记录
- 不允许"内存调用"绕过审计
- 即使是同进程内 Agent 协作也必须经此表

#### 表 4 · feedback_log（效果反馈日志）

回答**"预测准不准？"**

| 字段 | 含义 |
|---|---|
| `feedback_id` | 反馈 ID |
| `customer_id` | 客户号 |
| `report_id` | 报告号 |
| `predicted` | 预测值（例：评分 78） |
| `actual` | 实际值（例：3 个月后实际不良） |
| `deviation` | 偏差 |
| `observed_at` | 观测时间戳 |
| `feedback_type` | `repayment` / `default` / `manual_review` |

**关键约束**：
- 贷后跟踪必须回写
- 偏差用于 §3.2 表 5 自修正

#### 表 5 · improve_log（改进轨迹日志）

回答**"怎么修正的？"**

| 字段 | 含义 |
|---|---|
| `improve_id` | 改进 ID |
| `scope` | `agent` / `prompt` / `threshold` / `model_version` |
| `target_id` | 改动目标（如 `LE-A14`） |
| `change_summary` | 变更摘要 |
| `before` | 变更前配置 |
| `after` | 变更后配置 |
| `decided_by` | 决策人（人或自动）|
| `decided_at` | 时间戳 |
| `linked_feedback` | 关联的反馈记录（指向 feedback_log）|

**关键约束**：
- 任何 Agent / Prompt / 阈值 / 模型变更都必须留痕
- 包括灰度发布、AB 实验、紧急回滚

### 3.2 五表的因果链

```
device_pool/revenue_pool        cycle_log              agent_signal_log     feedback_log     improve_log
 ┃ 数据池快照                    ┃ 决策循环              ┃ 协作信号           ┃ 效果反馈        ┃ 改进轨迹
 ┃                               ┃                       ┃                    ┃                 ┃
 ┗━ Sense ━━━━━━━━━━━━━━━━━━━━━┻━ Decide ━━━━━━━━━━━━┻━ Act ━━━━━━━━━━━━┻━ Feedback ━━━┻━ Improve ━┓
                                                                                                       ┃
                                ┃                                                                      ┃
                                ┗━━ 闭环：Improve 的 after 配置驱动下一轮 Decide ━━━━━━━━━━━━━━━━━━━┛
```

监管的任何提问都可被映射到对这五张表的 SQL 查询：
- "基于什么数据决策？" → `device_pool` / `revenue_pool`
- "怎么决策的？" → `cycle_log`
- "Agent 之间如何协作？" → `agent_signal_log`
- "预测准不准？" → `feedback_log`
- "为什么这个阈值变了？" → `improve_log`

### 3.3 SQL 可查 = 监管可查

> "SDAFI 的 Audit-by-Design 不是产品白皮书里写得好看的承诺，而是**数据库表里能 SQL 查询的事实**"

合规部门不需要发邮件让科技部门去导日志——直接 SQL 查询五张表。这是**产品级别**的可审计性，不是文档级别。

### 3.4 与监管要求的映射（核心销讲点）

| 监管要求 | 来源 | SDAFI 对应能力 |
|---|---|---|
| 信贷决策模型输入输出留痕 | 银保监现场检查 | `cycle_log` + 数据池快照（精确到秒） |
| 可疑交易判定链路可查 | 反洗钱审计 | `agent_signal_log` 全量协作记录 |
| 自动化决策可解释性 | 《个保法》第 24 条 | 五表证据链 + 决策路径回放 |
| 穿透式监管 | 穿透式监管要求 | 数据来源 + 模型版本 + 决策结果三位一体 |
| 算法备案 | 网信办算法备案 | `improve_log` 记录所有模型参数演化 |
| 数据要素流通可审计 | 公共数据授权运营 | `agent_signal_log` 记录所有数据流向 |

## 4. 四条架构纪律

> 这是 SDAFI 区别于其他 Agent 框架的**关键工程纪律**。任何 SDAFI 实现都必须遵守。

### 纪律一 · 写入路径单一可追溯

**规则**：五个阶段中，**只有 Act 阶段被允许向业务库写入**，其他四个阶段严格只读。

**业务影响**：
- 任何业务数据变更都能精确追溯到唯一的 Act 操作
- 不会出现"这个数据改了但说不清谁改的"
- 跨 Agent 协作中，写入边界清晰

**反例**：通用 Agent 框架中，任何 Agent 都可以写数据库 → 出问题时无法定位是哪个 Agent。

**SDAFI 实现**：
- 业务数据库读写权限按阶段分离
- Sense / Decide / Feedback / Improve 阶段持只读凭证
- Act 阶段写入时强制带 `cycle_id` 关联

### 纪律二 · 状态变更可回滚

**规则**：每一次 Act 写入都对应**一次完整的 S→D→A 决策记录**，如果决策被认定有误，可以精确还原到决策前状态。

**业务影响**：
- 单笔授信若事后被认定有误（如发现欺诈），可精确还原数据状态
- 不会因"已经写下游了"导致数据污染扩大
- 重大故障可精确定点回滚

**SDAFI 实现**：
- 每次写入前记录 before（在 cycle_log）
- 写入后记录 after
- 回滚 = 逆向应用差异 + 写入新 cycle_log（标记 `rollback`）

### 纪律三 · Agent 间协作零直接调用，数据池为唯一介质

**规则**：所有 Agent 交互**必须经过 PostgreSQL 数据池**（具体为 `agent_signal_log` 表 + 数据池快照），不允许进程内调用、内存共享、自然语言对话。

**业务影响**：
- 每一次跨 Agent 协作都是一条 SQL 可查的结构化记录
- 即使部署多实例（横向扩展），所有审计证据汇集到同一查询面
- 监管要求查"18 个 Agent 之间是怎么协作做出决策的" → 给出完整结构化、可视化的协作时序图

**对比反例**：

| 框架 | 协作方式 | 监管可回溯性 |
|---|---|---|
| LangChain | 链式调用，进程内 | ✗ 仅有 prompt 日志，无结构化记录 |
| LangGraph / CrewAI | 节点间消息，进程内 | △ 有 message 但粒度粗，跨实例难一致 |
| **SDAFI** | **数据池表 + 信号日志** | ✓ **SQL 可查，跨实例一致** |

**SDAFI 实现**：
- Agent 间不允许直接 import / 函数调用
- 所有跨 Agent 数据流必须写入数据池 + 信号日志
- 异步唤醒可用 LISTEN/NOTIFY 或消息队列（具体实现不限定，但必须留痕）

### 纪律四 · 单一真相源（Single Source of Truth）

**规则**：即使部署多实例（横向扩展），所有审计证据**必须汇集到同一个查询面**，不得分散在各实例本地。

**业务影响**：
- 监管查询不必跨实例对账
- 不出现"实例 A 说审批通过、实例 B 说被拒"的灰色地带
- 即使某实例故障，审计证据完整保留

**SDAFI 实现**：
- 五张审计表存储位置统一
- 多实例的写入必须最终一致汇聚
- 业务方对实施方的查询要求：能否用一条 SQL 在所有实例的决策中检索

## 5. 与同类 AI Agent 框架的对比

> 我们将 SDAFI 与市场上主流的 AI Agent 框架在**审计能力**上做了系统性对比。这张表对银行风控合规部门判断技术选型有直接价值。

### 5.1 审计能力对比

| 审计维度 | LangChain | LangGraph / CrewAI | **SDAFI** |
|---|---|---|---|
| 决策输入留痕（基于什么数据） | ✗ 内存瞬态 | △ checkpoint 粗粒度 | ✓ **数据池快照带 timestamp** |
| 决策过程回放（规则命中） | ✗ 需额外日志 | △ 状态快照 | ✓ **cycle_log 完整记录** |
| 协作因果链（谁触发了谁） | ✗ 无结构化记录 | △ 节点间 message | ✓ **agent_signal_log 全量** |
| 效果验证轨迹（事后效果） | ✗ 不在设计范围 | ✗ 不在设计范围 | ✓ **feedback_log deviation** |
| 自修正历史（参数演化） | ✗ 无此概念 | ✗ 无此概念 | ✓ **improve_log** |
| 跨实例审计一致性 | ✗ 难以保证 | △ 需外部协调 | ✓ **单一真相源** |

> 注：✓ = 原生支持；△ = 需自行实现；✗ = 不在设计范围。

### 5.2 适用场景对比

| 场景 | 推荐 |
|---|---|
| 通用 chatbot / copilot | LangChain / LangGraph（灵活性强） |
| 内部 RAG 知识问答 | LangChain（生态丰富） |
| 多 Agent 协作演示 / 创意应用 | CrewAI（角色化抽象） |
| **金融业 / 能源 / 政务** | **SDAFI（监管级回溯）** |
| **银行授信决策** | **SDAFI（必备）** |

### 5.3 关键差异化论据

**论据一**：在通用 chatbot / copilot 场景里，SDAFI 未必是最优选择（LangGraph 的灵活性更强）。**但在银行业这种需要监管级回溯的场景里，SDAFI 是目前唯一开箱即用满足要求的 AI Agent 运行时**。

**论据二**：SDAFI 的优势**短期内无法被通用框架复制**。原因是：
- 通用框架的"灵活性"和"审计性"是矛盾的（灵活越高越难审计）
- 通用框架在事后加审计层 = 撕开重做
- 而 SDAFI 是**架构选择**，从第一行代码就考虑监管对接

**论据三**：选择 Agent 框架时，"审计能力"应与"技术能力"同等重要，甚至更重要。一个无法在产品架构层面把合规设计好的厂商，即使技术再先进也难以在银行业立足。

### 7.3 数据池快照在尽调的关键作用

**场景**：法人版尽调启动时，编排引擎并发调用 90+ API。这些数据在某一时点被冻结为快照。

**关键约束**：
- 18 个 Agent 看到的数据是**同一快照**（避免某 Agent 看到 14:33 的数据，另一个看到 14:35 更新后的数据导致结论矛盾）
- 快照不可变：即使 API 数据后续更新，本次报告依然引用快照值
- 快照保留至贷款清偿 + 5 年（监管查证可用）

**业务影响**：
- 报告**结论可重现**（同样的快照、同样的 Agent 版本 → 同样的结论）
- 决策可回放（监管 / 客户 / 内审随时复查）
- 客户授权撤回时，已生成报告依然有效（基于撤回前合法快照）

### 7.4 SDAFI 与产品质量保证

> SDAFI 不仅是合规工具，也是产品质量保证机制。

**质量保证 1**：**Agent 间因果链清晰** → 单 Agent 失败可精确定位影响范围

**质量保证 2**：**改进有据可依** → 每次 Prompt 调整都有 feedback 反向驱动，不靠"产品经理拍脑袋"

**质量保证 3**：**版本可对比** → 灰度发布时新旧版本输出 diff 可视化

**质量保证 4**：**回归无死角** → 任意历史报告可重放（用旧快照 + 新模型）做对比

## 8. SDAFI 的反模式与边界

> 任何强约束方法论都有适用边界。我们对 SDAFI 不适用或需要慎用的场景保持诚实。

### 8.1 不适用 SDAFI 的场景

| 场景 | 推荐替代 |
|---|---|
| 创意 / 头脑风暴类 AI 应用 | 用通用框架；SDAFI 的强约束反而限制创意 |
| 实时对话型客服（< 1s 响应）| SDAFI 写表开销可能影响延时 |
| 内部研发实验性 AI 工具 | 通用框架更敏捷 |
| 不涉及监管的纯效率类应用（如代码生成） | 不需要 audit-by-design |

### 8.2 SDAFI 的反模式

#### 反模式 1：把 SDAFI 当作单纯的"日志框架"

❌ 错：仅在调用前后加日志，不做架构纪律约束。

✅ 对：四条纪律必须严格遵守，否则审计性是假的。

#### 反模式 2：跳过 Feedback 阶段

❌ 错：上线后不跟踪贷后表现，五张表只用了三张。

✅ 对：贷后反馈是闭环的核心，没有 F 就没有 I。

#### 反模式 3：Improve 完全自动化

❌ 错：让模型根据 feedback 自动调整 prompt / 阈值。

✅ 对：Improve **必须有人类审批**，否则失控（特别是金融场景）。

#### 反模式 4：把所有数据都塞进数据池

❌ 错：为了"完整"把整个 API 响应原样存。

✅ 对：最小必要原则；只存与决策相关的字段。

### 8.3 工程开销

诚实声明：SDAFI 比通用框架**多 15-25% 的工程成本**：
- 五张表的存储与查询开销
- 严格的 Agent 间通信纪律
- 运维多张审计表
- 培训团队遵守纪律

> **金融场景下**，这部分成本相比"被监管处罚 / 业务暂停整改" 的代价微不足道。

## 9. 技术实施约束（业务层）

> 本章定义对实施方的**业务层约束**，**不规定具体技术选型**。

### 9.1 必须满足的业务约束

| 约束 | 验证方法 |
|---|---|
| 五张审计表在业务层呈现一致 | 单笔决策 → 五表 SQL 检索 → 完整证据链 |
| 数据池快照不可变 | 修改尝试触发审计告警 |
| Agent 间无直接调用 | 代码审查 + 进程内调用监测 |
| 写入路径单一（仅 Act）| 数据库权限分离审计 |
| 跨实例单一真相源 | 不同实例的查询结果一致性测试 |
| 审计回放 ≤ 30 秒 | 性能测试 |

### 9.2 实施方可自主选择的事项

实施方可根据银行环境自主选择以下技术：
- 数据库类型（关系型 / 时序型 / 文档型 / 混合）
- 消息中间件（RabbitMQ / Kafka / 行内 ESB / 直接 DB LISTEN/NOTIFY）
- 部署形态（单体 / 微服务 / Serverless）
- Agent 编排引擎（自研 / 改造开源）
- 大模型路由层（云 API / 本地推理 / 混合）

**唯一硬性要求**：满足 §9.1 的业务层约束，并通过审计能力验收。

### 9.3 与行内系统集成约束

| 集成点 | 约束 |
|---|---|
| 客户中心（CIF） | Sense 阶段读取，写入数据池快照 |
| 信贷核心 | Act 阶段回写，与 cycle_id 关联 |
| 行内审计平台 | 五张表数据可同步至行内审计系统（同步方式由实施方对齐）|
| 监管报送 | 审计包导出格式由行内合规部确认 |

## 10. 行业案例与论据

### 10.1 案例 · 华南某地级市国有大行普惠金融示范区

**项目规模**：35 万个体工商户 + 10 万小微企业批量授信

**SDAFI 在此项目的关键作用**：

#### 作用 1：35 万次授权全程留痕

每个客户的授权链条（H5 实人核身 + 电子签约）写入 `agent_signal_log` + 数据池授权字段。**4 个月内 45 万次授权 100% 可追溯**。

#### 作用 2：跨 4 个月、35 万户的报告稳定性

每份报告的所有 Agent 决策都基于当时的数据池快照 + 当时的 Agent 版本。**4 个月内多次 Agent 版本升级**，但已生成报告的结论可完整复现。

#### 作用 3：监管现场抽样

当地银保监对项目进行**抽样检查**：随机抽 10 笔授信，要求当场调出决策依据。

**SDAFI 应对**：
- 每笔抽样 SQL 检索 → 时序图 → 证据下钻
- **平均耗时 22 秒 / 笔**
- 监管现场认可（"这是我们见过最系统的 AI 审计能力"）

#### 作用 4：批量授权撤回响应

项目周期内累计 ~ 1,200 次客户授权撤回。SDAFI 在 24 小时内停止后续 API 调用 + 通知银行 + 留痕。

> **关键数据**：本项目中 SDAFI 五张审计表合计写入 **17 亿条记录**。监管 / 内审请求平均处理时间 **18 秒 / 笔**。

### 10.2 论据 · 五对交叉验证的内部回测

> 基于金智维在多个批量授信项目中累计 50,000+ 样本的内部回测数据：

- 五对交叉验证识别出的"高风险样本"最终违约率 **8.7%**
- 其它经过五维评分通过的样本违约率 **0.4%**
- 风险密度提升 **约 20 倍**

> 这些回测数据都是 SDAFI 的 `feedback_log` 长期沉淀的产物 — 没有 SDAFI，就没有这种系统性回测能力。

### 10.3 论据 · Agent 错误归因效率

不使用 SDAFI 的 Agent 系统出现"某客户被误判"时，定位原因平均耗时 **2-3 工作日**（需翻日志 / 复现 / 询问开发）。

使用 SDAFI 的相同场景：

```sql
-- 30 秒内拿到完整证据链
SELECT cycle_log.*, agent_signal_log.*
FROM cycle_log
JOIN agent_signal_log ON ...
WHERE customer_id = 'misjudged-A'
ORDER BY started_at;
```

→ 定位原因 **平均 8 分钟**。**效率提升 100x**。

## 11. 未来演进

### 11.1 v2.0 → v3.0 演进方向

| 方向 | v2.0 | v3.0 计划 |
|---|---|---|
| 多模态数据池 | 结构化数据 | + 文档 / 图像 / 音频快照 |
| 自动 Improve | 人工驱动 | 半自动（基于 feedback 自动建议变更，人类审批）|
| 实时反馈 | 月度 | 实时（流式 feedback）|
| 跨产品复用 | 智慧信贷 | 涵盖反洗钱 / 投顾 / 客服 |
| 监管直连 | 手动报送 | 与监管系统标准化对接 |

### 11.2 与大模型演进的关系

SDAFI 与具体大模型解耦。任何大模型（GPT / Claude / DeepSeek / Qwen / 自研）都可以作为 Decide 阶段的执行引擎，**SDAFI 的方法论不受影响**。

随着大模型能力提升：
- Agent 数量可能减少（一个强大 Agent 替代多个）
- 但**五阶段 + 五张表的纪律不变**
- 反而更需要审计性（更强的能力 = 更高的可解释性要求）
